# 烧token模式（回复前自主准备 · 可后台切换）

> **状态：✅ 已实现 + 真机实测通过（2026-09-22）** —— 开关在面板「烧token模式」，或配置 `Bot.BurnToken.Enabled`。
>
> **一句话**：正式开口前，先给她一段"能查资料、能自己判断够不够"的时间。起始上下文只放必需信息（人设 + 基本提示词 + 唤起原因），历史与记忆**都不注入**，由她自己调工具去取；**只有调用 `ready_to_reply` 之后的输出才算正文**。做成后台可切换的独立模式——关掉开关即回到原有行为，一个分支都不进。

主人原话：
> 适当增加静静在正式回复前的准备轮数，起始只放必要的信息，然后让静静自己去调用聊天记录了解情况，自己判断需不需要调用工具，自己判断在输出之前还需要做什么准备，以及自己掌握的消息是否已经可以正式输出了。

---

## 1. 现状：她想做的三件事，现在都缺一环

| 她想要的 | 现状 | 缺什么 |
|---|---|---|
| **准备轮数**要多 | 规划轮只有 **1 次**（`Planning.Enabled`，且**默认关**） | 只有一轮，没有"查完再看够不够"的余地 |
| **自己调工具了解情况** | 规划轮是 `CompleteAsync` 纯文本调用，**不带 tools** | **只能"想"，不能"查"** ← 关键缺口 |
| **起始只放必要信息** | 私聊**注入完整历史**（≤50 条） | 一开始就把话都说完了，她没必要自己去取 |
| **自己判断能否输出** | 没有"我准备好了"这个信号 | 程序不知道她准备到哪一步了 |

一句话：**现在的"规划"是闭卷考试，她要的是开卷。**

## 2. 现状链路（读码，非推测）

| 项 | 现值 | 位置 |
|---|---|---|
| 工具轮上限（普通对话） | `Llm.MaxToolRounds = 6` | `BotOptions.cs:399` |
| 工具轮上限（自主活动） | `AutoActivity.MaxToolRounds = 8` | `BotOptions.cs:477` |
| 会话保留条数 | `MaxContextMessages = 50`（类默认 20） | `appsettings.json` / `BotOptions.cs:542` |
| 私聊起始上下文 | **注入完整历史**（`_context.BuildMessages`） | `EventDispatcher.cs:753-756` |
| 群聊起始上下文 | 外置（`AutoInjectGroupHistory=false`）+ 提示"有 N 条，自己调工具取" | `EventDispatcher.cs:687-693` |
| 规划轮 | 1 次纯文本调用、**无 tools**、默认关 | `EventDispatcher.cs:1172-1191` |
| 单次回复条数 | `Reply.MaxRepliesPerTurn = 4` | `BotOptions.cs:205` |

现有主循环（`EventDispatcher` 第 838 行起）骨架：

```
while (true) {                                  // 外层：工具轮（≤6）
    messages = BuildRequest()                   // system + 历史/当前消息 + roundMsgs + 格式指令
    result   = LLM(messages, tools)             // 带 tools
    ├─ 回复数组        → 逐条 SendItemAsync → 结束
    ├─ 原生 tool_calls → 先发 spoken(若有) → 执行工具 → 结束当前轮，外层继续
    ├─ 普通文本        → SendItemAsync → 结束
    └─ 格式垃圾        → 带纠正提示重试（≤2 次）
}
```

⚠️ **一个必须注意的既有行为**：每轮产出的正文**都会被发出去**（`SendItemAsync`，第 894 行连"带 tool_calls 那轮的 spoken"也发）。所以"准备了半天、中间那几句碎碎念全飘到主人眼前"是必然会发生的——**新模式必须有静默机制**。

## 3. 新模式设计

### 3.1 三阶段

```
① 瘦身起始            ② 准备循环（静默，≤N 轮）           ③ 正式回复（沿用现有逻辑）
─────────────         ─────────────────────────          ──────────────────────
人设 / 时间             她能在这里：
对方是谁（昵称/身份）     · 调 get_chat_history 看聊天记录     现有回复数组 → 逐条发送
相关记忆注入             · 调 search_memory 翻记忆库          （工具轮也照旧）
上一轮规划（可选）       · 调 read_file 读自己空间的文件
"你有 N 条历史记录，     · 调 get_time 等其他工具
 要不要看自己决定"       · 什么都不做，直接说"我准备好了" ────┘
                        ↑ 全程只说给程序听，不发出去
```

### 3.2 静默准备轮——"只查不说"怎么落地

准备阶段**单独一个循环**，与现有回复循环完全隔离：

- 每轮照常请求 LLM（带工具），但**只接受两类产出**：
  1. 工具调用 → 执行 → 结果回填 → 继续下一轮
  2. `ready_to_reply` 工具调用 → 准备结束
- 她这一轮吐出的**任何文字正文都不发送**（保留在对话历史里当"她的思路"，不影响 DeepSeek 的 `reasoning_content` 完整回传要求）。
- 如果她既没调工具、又没说 ready（例如只回了一句话）→ 判定为"她其实想直接说" → **直接把这句话交给正式阶段**，不浪费。

### 3.3 收敛信号：`ready_to_reply`

新增一个无参工具，**只在准备阶段注册**：

```csharp
public sealed class ReadyToReplyTool : ITool
{
    public string Name => "ready_to_reply";
    public string Description =>
        "声明你的准备工作已完成、可以正式回复了。准备工作阶段结束时**必须**调用本工具；" +
        "如果你觉得信息还不够，请先调用其它工具去查，不要过早调用本工具。";
    public JsonObject ParametersSchema => new()
    {
        ["type"] = "object",
        ["properties"] = new JsonObject(),
        ["additionalProperties"] = false
    };
    public Task<string> ExecuteAsync(string argsJson, ToolContext ctx, CancellationToken ct)
        => Task.FromResult("已收到，现在进入正式回复阶段。");
}
```

为什么不靠特定文本标记（如 `[[READY]]`）：**判断脆弱**——她多打一个空格、换个说法就认不出来，而认不出来就只是白等一轮。工具调用是结构化的，可靠得多。

平时（正式阶段）**这个工具不在清单里**，所以她不会在正常聊天里乱调它。

### 3.4 三条兜底（缺一不可）

| 情况 | 处理 |
|---|---|
| 轮数用尽还没 ready | 直接进正式回复（不卡死） |
| 准备循环抛异常/超时 | 捕获 → 直接进正式回复（**绝不能让新模式把回复搞崩**） |
| 工具执行失败 | 把失败信息回填给她 → 她自己决定继续查还是放弃 |

整体包一层 `try/catch`，异常只打日志、静默降级。

### 3.5 上下文怎么衔接

准备阶段的 `roundMsgs`（assistant 的 tool_calls + tool 结果）**原样带进正式循环**——她刚查到的东西必须在正式请求里看得见，否则白查了。

正式阶段的上下文 = `瘦身 system` + `当前消息` + `准备阶段的 roundMsgs` + `格式指令`。

### 3.6 为什么不动现有循环

新代码全部放在现有 `while (true)` **之前**，独立函数 `RunPrepareLoopAsync(...)`：

```
if (_options.Prepare.Enabled && 适用场景)     // ← 唯一的侵入点，一个 if
    await RunPrepareLoopAsync(...);           // 新代码，失败即静默返回

... 现有逻辑原封不动 ...
```

开关关闭时，**一个分支都不进**，现有行为逐字节相同。这也正好满足主人"保留现在已有的"。

⚠️ **热更新注意**：`Prepare.*` 是 `BotOptions` 的嵌套子对象，面板改写是**原地改引用**，所以运行时要**每轮重读** `_options.Prepare.Enabled`（不能像 `AutoActivityService` 那次一样启动时读一次就存着——那个坑已经吃过）。

## 4. 配置与面板

新增 `Bot.Prepare` 段，面板新增一个组，**直接放在现有「规划轮」组旁边**——这样它天然就是一个"测试模式"：

| 配置项 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `Prepare.Enabled` | bool | **false** | 模式总开关（组开关）。关 = 完全走现有链路 |
| `Prepare.MaxRounds` | int | **3** | 准备轮上限（1~8） |
| `Prepare.SkipHistory` | bool | **true** | 起始**不注入**完整历史，改成"有多少条、要不要看自己决定" |
| `Prepare.IncludeGroup` | bool | **false** | 是否对群聊也启用（群里有别人在等，默认只对私聊/主人） |
| `Prepare.Prompt` | text | 空=内置 | 准备阶段提示词模板；`{Tools}`=工具摘要、`{UserText}`=对方消息、`{HistoryCount}`=历史条数 |

面板组的写法（与现有 `planning` 组同构）：

```csharp
new("prepare", "自主准备（测试）", "回复前让她自己去查资料、自己判断够不够，再正式回复", ["Prepare", "Enabled"],
[
    new CfgItem(["Prepare", "MaxRounds"],    "准备轮上限", "最多让她查几轮（查完自己说准备好了）", "int"),
    new CfgItem(["Prepare", "SkipHistory"],  "起始不注入历史", "开=只告诉她有多少条、让她自己决定看不看；关=照旧注入完整历史", "bool"),
    new CfgItem(["Prepare", "IncludeGroup"], "群聊也启用", "群里有别人在等，默认只对私聊生效", "bool"),
    new CfgItem(["Prepare", "Prompt"],       "准备阶段提示词", "{Tools}/{UserText}/{HistoryCount}；留空=内置默认", "text"),
]),
```

**与旧「规划轮」的关系（待拍板）**：建议 `Prepare.Enabled=true` 时**自动跳过旧规划轮**——准备循环本身就是"带工具的升级版规划"，两个一起跑等于白花一次调用。

## 5. 提示词草案（准备阶段）

```
现在不是让你回复，而是让你【准备】。对方的话是：

【对方消息】{UserText}

【你可用的工具】
{Tools}

【关于资料】你这次只拿到最必要的信息。这个会话还有 {HistoryCount} 条聊天记录没有给你，
需要的话用 get_chat_history 自己取（一次能拿到的量是配置好的，不够就再取别的工具查）。

请你判断：
1. 就凭现在手里的信息，能不能给出一个好的回复？缺什么？
2. 缺的东西，用哪个工具能查到？去查（可以连着查几轮）。
3. 查完确认足够之后，调用 ready_to_reply 进入正式回复。

注意：
- 这个过程对方是看不见的，你在这里说的话不会发出去，所以不要在这里写正式回复。
- 不要为了"显得认真"而查工具；直接就能答好的话，立刻调用 ready_to_reply。
- 你已经查了 {RoundsUsed} 轮，上限是 {MaxRounds} 轮，到上限会直接进入正式回复。
```

## 6. 代价与风险

| 风险 | 说明 | 应对 |
|---|---|---|
| **首字延迟上升** | 每多一轮 = 多一次 LLM 往返；她要是查 3 轮，主人要多等好几秒 | 默认 `MaxRounds=3`；先只对私聊开 |
| **成本上升** | 准备轮的 token 照常计费，且每轮都带完整 system | 与"瘦身起始"配合正好抵消 |
| **她查上瘾 / 原地打转** | 反复调同一个工具 | 轮数硬上限兜底；提示词里点明"别为了显得认真而查" |
| **她干脆不查** | 所有消息都直接 ready，模式等于白开 | 日志能看到"准备 0 轮"，据此调提示词 |
| **群聊场景不合适** | 别人在群里等着，多几秒观感差 | 默认 `IncludeGroup=false` |
| **她的话被漏发** | 静默机制把她的正文吞了 | 仅吞"准备阶段"的正文；一旦进正式阶段恢复发送（见 3.2 的第 3 条） |

## 8. 验证方案

**A/B 对照**（同一条消息，开关各跑一次）——用"必须查历史才答得上来"的消息最能说明问题：

| 用例 | 期望 |
|---|---|
| "刚才说到哪了？" | 新模式：日志出现 `get_chat_history`；旧模式：直接凭注入的历史回答 |
| "我上次让你记的那个是什么来着" | 新模式：`search_memory`；能查到 → 回复内容更准 |
| "在吗"（寒暄） | 新模式：**0 轮准备直接 ready**（不该为寒暄去查资料） |
| 把 `MaxRounds` 设 1 且暗示她"别急着 ready" | 应看到 `轮数用尽，直接进入正式回复`，且**回复正常发出**（兜底生效） |
| 关掉开关 | 日志无 `[准备]` 任何行，行为与改动前一致 |

**兜底专项**：临时把 `MaxRounds` 设 0 / 准备阶段用一条超长历史让她反复查——确认不会卡死、不会漏回复。

## 10. 拍板结论（2026-09-22 主人定的 7 条）

| # | 主人原话 | 落地 |
|---|---|---|
| 1 | 名字就叫**「烧token模式」** | 面板组「烧token模式」，配置段 `Bot.BurnToken` |
| 2 | 操作上限给到 **30 轮**，可随时在后台改 | `BurnToken.MaxRounds = 30`，面板可改、运行时每轮重读 |
| 3 | **忽略一切旧模式额外轮和提示词插入效果** | 规划轮 / 上一轮规划注入 / 群历史注入 / 记忆摘要注入 / 私聊历史注入，全部跳过 |
| 4 | 先适用私聊，**保留可适用于群聊**的能力 | `ScopePrivate=true`、`ScopeGroup=false`（另加 `ScopeGuest=false`：未知客人不发散烧 token） |
| 5 | 记忆**不注入**，让她自己用关键词查，还要能知道自己哪些记忆没有/不对/该修改 | 不注入记忆；`search_memory` 增加**盘点模式**（空关键词列清单 + 总条数 + #id）；新增 `update_memory`（改内容/重要度，不能删） |
| 6 | **忽略思考轮的一切输出**，只有 `ready_to_reply` 之后的输出才是正文；正文后保留全部上下文给她自评 + 整理记忆 | 收集轮正文一律不发送（含自言自语，继续请求）；正文后 `SelfReview` 轮 |
| 7 | 完整流程（唤起 → 人设 → 唤起原因 → 工具+操作建议 → 思考/收集 → 正文；超限=强制 ready） | 见 §3、§11 |

## 11. 已实现（文件清单）

| 文件 | 改动 |
|---|---|
| `Core/Options/BotOptions.cs` | 新增 `BurnTokenOptions`（Enabled/MaxRounds/ScopePrivate/ScopeGroup/ScopeGuest/SelfReview/SelfReviewMaxRounds/Prompt）+ 挂载到 `BotOptions.BurnToken` |
| `Core/Tools/BuiltinTools.cs` | 新增 `ReadyToReplyTool`（**OwnerOnly**，只在烧token模式出现）、`UpdateMemoryTool`（OwnerOnly）；`SearchMemoryTool` 改造为「检索 + 盘点」，改用范围受限查询 |
| `Core/Memory/Database.cs` | 新增 `SearchScopedMemories(qqId, groupId, keyword, limit)`：范围 = global + 该用户 + 该群（**不跨用户泄漏**），同时返回总条数 |
| `Core/Dispatcher/EventDispatcher.cs` | `burn` 判定；6 处旧效果隔离；`RunBurnPrepareAsync`（收集循环）、`BurnRoundAsync`（单轮）、`RunBurnSelfReviewAsync`（自评轮）、`ExtractBurnToolCalls`（两种工具调用格式）、`BuildBurnPrompt`、`RemoveTool` 及两段内置提示词 |
| `Core/Admin/AdminService.cs` | 面板新增「烧token模式」组（8 项），紧挨「规划轮」 |
| `appsettings.json` | `Bot.BurnToken` 段（8 个键，面板 PUT 才能写进去） |

**隔离方式**：新代码全在现有回复循环**之前/之后**，唯一侵入点是 `if (burn)` 与几处 `&& !burn`；`burn=false` 时一个分支都不进。

**两个顺手修掉的隐患**：
1. `Database.LoadMemories(..., includeGlobal:true)` 的实现是"不加 WHERE"→ **会捞出所有用户/所有群的记忆**（而 `search_memory` 正是唯一调用者）。已改用 `SearchScopedMemories`，并在旧方法上留了警告注释。
2. `ready_to_reply` 平时会出现在她的工具清单里（她平时根本用不上）→ 非烧token模式下一律从清单移除。

## 12. 实测（真机，走 `/api/pet/chat` → 主人私聊链路）

| 用例 | 结果 |
|---|---|
| **超限强制分支**（`MaxRounds=3`，"你还记得我们之前聊到过什么吗"） | 16.3s / 4 条正文。日志：第1轮 `get_chat_history`+`search_memory`+`get_time` → 第2轮 `capture_screen`+`read_file` → 第3轮 `read_file`×2 → **`3 轮用尽仍未调用 ready_to_reply → 强制进入正式回复`** → 4 条正文（内容含真实历史细节，证明确实查到了）→ 自评 2 轮 |
| **主动 ready 分支**（`MaxRounds=8`，"现在几点了？"） | 7.7s / 1 条正文。日志：第1轮 `get_time` → 第2轮 `ready_to_reply` → **`信息收集完成（第 2 轮 ready_to_reply，耗时 1.0s）`** → 正文正确（00:32 星期二）→ 自评 3 轮，**并真的动手整理了记忆**（发现 #281 与 #282 同义重复，用 `update_memory` 加注） |
| **静默验证** | 日志里她输出过 `I'll check the current time.` 及两段自评文字 —— **主人只收到 1 条气泡**（正文），其余全部未发送 ✓ |
| **关闭开关** | 本轮日志**无任何 `烧token` 行**，行为与改动前一致 ✓ |
| **记忆范围** | `search_memory` 报"你范围内的记忆共 **25** 条"= global 8 + 主人 user 17 ✓（旧的查全表会报 31，含别的群的 6 条） |

## 13. 实测暴露的三个问题（都不在烧token模式里，供后续决策）

1. **关掉开关时她会刷屏**：同一条"现在几点了"，非烧token模式下发了出来 **15 条**，大量近义重复（"这个点还不去睡"重复 5 次）。原因：她的"回复数组"里夹着 `tool_calls`，多轮 agent 循环里每轮都发言，而"逐字相同"去重拦不住换了个括号描述的近义句。**烧token模式反而没这个问题**（收集轮全静默，正文只输出一次）。
2. **她自己撞上了 `read_file` 的 3000 字上限**：自评里原话——"工作区日志只读到 3000 字符就被截断，09-21 之后的活动记录没看完"。这正好印证《上下文瘦身方案》P0（`read_file` 加分段读）的必要性——**她已经开始需要这个能力了**。
3. **她"查上瘾"**：`MaxRounds=3` 时她连"你还记得吗"都要查满 3 轮；连"现在几点"这种自足问题，第 1 轮她也先纠结"要不要查历史"。30 轮上限意味着**极端情况下单条消息要等 1~3 分钟**——建议先把轮数控制在 5~8 观察，或用 `Prompt` 调教她"自足问题直接 ready"。
